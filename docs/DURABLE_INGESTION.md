# Phase 05 synthetic durable ingestion

## Phase 05-F committed-generation dispatch

[DurableDispatch](../backend/app/realtime/dispatch.py) implements a durable, metadata-only queue for **already accepted synthetic generations**. It dispatches the SQL-authoritative latest checkpoint into its exclusive Redis tracking namespace. It does not queue raw protobuf input before acceptance, fetch feeds, store historical checkpoint copies, deliver to clients or start with the API. Existing ingestion acceptance still requires its SQL commit and existing Redis work. Unaccepted process-local bytes still require producer resubmission; this slice makes no raw-ingress crash-survival promise.

Additive [0005](../backend/migrations/versions/0005_ingestion_dispatch.py), over unchanged 0003/0004, adds private `ingestion_dispatch` references and owner-controlled source policy columns. Defaults: **8 total retained jobs per source**, **3 attempts**, **10-second lease**; hard ranges 1–32, 1–5 and 1–60 seconds. All retained rows, including terminal outcomes, consume capacity, so replay/duplicates cannot grow a hidden metadata archive. Saturation returns `backpressure` without changing accepted source evidence/watermarks or evicting jobs. These conservative fixture limits are not a production throughput policy. Source registration/count is owner-controlled; there is no global multi-source admission quota yet. Workers cannot change the policy columns or job identity/binding/deadlines. Review the updated [group grants](../backend/sql/ingestion_role.sql) explicitly; for an already provisioned group apply reviewed GRANT lines rather than rerunning CREATE ROLE. Migrations create no roles, assignments or credentials and API grants deny the new table. There are now 31 RLS-enabled tables.

Call `enqueue(now=...)` after successful durable acceptance and again on producer/dispatcher reconstruction to reconcile a commit-to-enqueue crash gap. Admission accepts no source, payload, URL or generation supplied by a request: it reads the configured source's current committed watermark, unexpired matching acceptance evidence and validated checkpoint. Identity is the existing accepted-generation digest; duplicates do not reset due time, receipt, deadline or attempts. It pins header/receipt, static binding and retained-guard digests, not a copy of position payloads. If several generations were accepted before reconciliation, only the current generation is eligible: intermediate generation delivery is not promised.

`claim(now=...)` serializes through the existing source advisory lock and commits one random lease token and incremented attempt before returning. `process(lease, now=...)` acquires the same source lock, verifies source/token/attempt and lease time, validates the current source/evidence/checkpoint and job reference, projects with original observation/alert TTLs, then commits acknowledgement. The lock spans projection and acknowledgement, preventing another claim or newer generation from racing that validation. A newer watermark retires an older job as `superseded` without projecting it. Corrupt references return `invalid` or unavailable; corrupt SQL/Redis state fails closed. Completed duplicate acknowledgements also revalidate integrity. Missing GPS and withdrawn/stale trip evidence remain unknown; all result/lease/snapshot labels remain simulation.

`run_one(now=...)` is one explicit claim/process tick, without sleep, thread creation or startup wiring. A process crash leaves the committed lease reclaimable after its deadline, consuming an attempt. Late tokens cannot acknowledge a replacement lease. Redis failure retries after 1/2/4/8 seconds up to the source attempt limit, then `exhausted`. SQL failure leaves the previously committed lease until expiry; ambiguous admission retries as duplicate, ambiguous claim waits/reclaims, and ambiguous acknowledgement reads the committed job rather than claiming success from Redis alone. SQL and Redis are not a distributed transaction. Existing durability-gated reads/maintenance remain mandatory; standalone cache access can bypass authority. A completed job is not automatically reopened after cache loss: existing scheduled recovery restores the trusted checkpoint, while pending jobs retry through dispatch.

Job deadlines derive from the **original** receipt plus the existing source evidence policy (900–86400 seconds), never enqueue/claim/retry time. Recovered payloads still expire at their original observation/alert deadlines (at most 900 seconds). Claims cannot replay an expired job; watermarks outlive job deletion. `retain(now=...)` removes only this source's expired metadata, and requires both supplied time and database `statement_timestamp()` to permit physical deletion. Admission opportunistically performs the same cleanup. Operate dispatch retention explicitly alongside existing maintenance: nothing silently installs a scheduler. All workers must use synchronized aware clocks; processing rejects a time before its committed claim. Database-owner and own-source worker trust assumptions remain as documented above.

0005 upgrades/downgrades run only in new disposable test databases. Downgrade deletes queued/terminal metadata and the three source dispatch policy columns; it preserves existing evidence/checkpoints/static bindings. Current workers require 0005; earlier API routes remain compatible with 0002–0005. No persistent application/Auth schema is migrated by this task. [Dispatch tests](../backend/tests/test_realtime_dispatch.py) exercise real PostGIS/Redis, source RLS, concurrent claimants, an actual child process exiting after lease commit, ambiguous commits and recovery. Exact results are in [Phase 05-F evidence](evidence/phase05-dispatch-2026-11-15.json).

Next: operator-driven multi-source orchestration/reconciliation with a global admission budget and operational metrics, then separately gated authenticated scoped delivery/active-journey foundations. Network fetch/raw-ingress durability still needs explicit producer/spool privacy and URL/rights review, bounded fetch/redirect/timeouts and crash/deletion tests. No source activation, mobile, wallet/QR, Phase 06 or production readiness is implied.

## Phase 05-E source-scoped workers and scheduled operations

This section supersedes the owner-only/unscheduled limitations in the historical Phase 05-D description below. Additive [0004](../backend/migrations/versions/0004_ingestion_scope.py) leaves [0003](../backend/migrations/versions/0003_realtime_durable.py) frozen. It adds private owner-assigned `ingestion_workers`, a security-barrier scope view, restrictive RLS and database-clock-expired evidence deletion. No roles, credentials, assignments or registrations are created by migration. Downgrade removes only these additions, preserving 0003 sources/evidence. API readiness accepts 0002/0003/0004. No persistent application/Auth migration is performed.

The explicit [provisioning script](../backend/sql/ingestion_role.sql) grants a NOLOGIN group required static/private SELECT, generation INSERT, expired-generation DELETE, and UPDATE only on source watermark/checkpoint columns. The owner alone registers sources and assigns exact database-role/source pairs. Workers cannot insert sources, alter bindings/dataset IDs/retention policies, update generation evidence or change assignments. Use a dedicated non-owner/non-superuser/non-BYPASSRLS login without API, owner or other worker-login membership. The shared group has no assignment and fails closed when selected directly. Remove assignments before reusing a dropped role name.

Scope uses actual `current_user`, never caller-set user/role/source GUCs. Restrictive policies intersect existing permissive catalog policies on **all 13 static tables**, including under spoofed admin GUCs and accidental SELECT grants. An owner-executed security-barrier view joins assignments/sources/datasets, filters by invoker `current_user`, and exposes only assigned source/dataset/feed IDs. Unlike a SECURITY DEFINER function, a view does not change `current_user`. Its sole PUBLIC privilege is SELECT; normal API callers need no private table access to evaluate catalog RLS. Existing verified API behavior stays covered by regressions. Keep the schema outside Supabase exposed schemas.

Existing source locks and exact static checksum/manifest/version/trip/calendar/cache-policy/namespace validation gate all operations. Generation DELETE additionally requires `expires_at <= statement_timestamp()`; a future caller clock cannot authorize deletion of unexpired evidence. Workers remain trusted to process their own assigned synthetic evidence: this isolates sources, not a malicious worker's fabricated own checkpoint. Owners remain trusted.

[IngestionMaintenance](../backend/app/realtime/maintenance.py) is explicit operator code for one preconfigured source: call `tick(now=...)`, or `run(stop_event, max_ticks=...)`. Nothing starts with the API. Each due tick performs at most one retention and one recovery transaction using the existing source lock, 2-second statement/1-second lock timeouts, at most 1000 evidence rows and bounded checkpoint/Redis attempts. Default cadence is 60 seconds (range 1–900). Retry delays are 1/2/4/8 seconds, maximum five attempts (default four), then wait for the next cadence. A tick never sleeps. The stoppable loop checks once per second and requires a finite 1–86400 tick budget. Ordinary exceptions become sanitized results; interruptions propagate. A mutex serializes same-instance ticks; independent instances serialize SQL through source advisory locks. Local retry/due state resets on reconstruction; there is no durable scheduler/leader election.

Retention preserves watermarks; recovery preserves original receipt times and observation/alert deadlines. Retry/reconstruction cannot renew GPS/service TTLs. Missing/stale evidence remains unknown. Physical SQL deletion requires this explicit operating cadence; no installed service, approved production policy or WAL/backup erasure is claimed.

Genuine [PostGIS/Redis worker tests](../backend/tests/test_realtime_worker.py) use non-owner `SET ROLE` execution without creating passwords. They cover spoofing, static/source isolation, prohibited changes, future-expiry deletion denial, retry/stop/concurrent ticks and migration rollback. Full regressions retain normal API RLS and Alembic schema comparison. This does not certify deployment login credentials or multi-host operations.

## Authority and ordering

`DurableIngestion(engine, cache, dataset_id)` wraps the existing `RedisFullDataset`, and the existing bounded `FullDatasetWorker` accepts this store. Use an exclusive synthetic Redis namespace; do not bypass the durability gate with standalone writers/readers. `register()` is explicit owner code, not request authorization. It binds one exact source, fixture trip/service-day scope, Redis policy/namespace, immutable validated synthetic static dataset ID/checksum/manifest/version and referenced trip/calendar facts. Binding changes require a separately registered source, not an in-place rebind. It never fetches or activates a feed.

PostgreSQL advisory transaction locks serialize each source with bounded lock/statement timeouts. Accepted/rejected/out-of-order/conflicting/quarantined generation metadata uses deterministic outcome/content identity; duplicate receipts do not create evidence or extend retention. No raw feed bodies/provider text are archived. Invalid/oversized input is bounded; oversized bodies reject before hashing and are not audited. Fixed per-source audit capacity rejects new work until explicit retention; watermarks never reset when audit rows expire.

The sole normalized recovery checkpoint contains the latest generation and original observation/receipt/alert deadlines plus bounded hash/order guards, not a historical location log. It is integrity-hashed and checked against the durable watermark and static binding. Redis changes remain provisional until SQL commits. A crash/SQL failure after a Redis write is not acceptance: every durable read/retry restores the last committed checkpoint while holding the source lock. SQL and Redis are not a distributed transaction. Do not expose standalone cache snapshots as durable reads.

Retained guards have a separate digest in the source watermark and accepted audit evidence, including guards for omitted channels that have no current observation record. An unexpired accepted audit must exist and match the watermark's receipt/header/content/guard digests before recovery. After metadata evidence expires, the durable source watermark and guard commitment remain. These consistency checks are not protection from a malicious database owner rewriting every commitment; owner/worker separation and production trust hardening remain required. When optional GTFS-RT route/direction references are present, they must match the bound immutable static trip as well as its service day.

Recovery validates binding/checkpoint/generation integrity before projecting original-deadline payload TTLs; it never renews GPS/trip evidence. Metadata may be reprojected after payload expiry to enforce durable header ordering. Missing/expired GPS, omitted entities and cache loss remain unknown, never cancellation. Only fresh independent synthetic trip evidence can indicate simulated cancellation; no graph authority is granted. A corrupt Redis manifest fails closed for owner investigation rather than being automatically deleted; an intact but provisional Redis generation can be replaced from committed durable state.

## Retention and operation

Registration defaults to 24-hour metadata evidence, bounded to 900–86400 seconds, and at most 1000 generation rows per source. `retain(now=..., apply=False)` reports this source's expired audit rows and recovery payloads; `apply=True` explicitly deletes expired rows and removes payloads whose original observation/alert deadlines passed. It retains the source binding and header watermark, including after all payloads/audits expire. Source count is owner-controlled. No scheduler is installed: operators must run retention within their approved cadence, and WAL/backups/storage-level erasure require privacy/operations review. These are synthetic development policies, not approved production rider retention.

Use the existing ignored owner configuration privately; never paste URLs, credentials or dump contents into evidence. Owner migrations use `python -m alembic upgrade head` only after reviewing effects and database target. No production activation, wallet, QR, authenticated delivery, active-journey schema or Phase 06 functionality is added.
